## 1. Exit Criteria Recap

Per `release/milestones.toml`, the four exit criteria for v0.5.0-beta.1 are:

| # | Criterion | Implication |
|---|-----------|-------------|
| 1 | **Fresh VM install succeeds** | We need an *installer* flow — not just a pre-built disk image that boots, but a mechanism that writes the OS onto a blank disk and the result boots. |
| 2 | **Installed system boots twice cleanly** | The installed system must survive a clean reboot cycle: systemd reaches `multi-user.target`, `optid.service` starts, and the boot assessment marker survives across reboots. |
| 3 | **Update and rollback tests pass** | `tools/test-rollback.sh` must pass on the installed system (or a disk image built via mkosi), validating UKI rotation, rollback entry retention, and bad-kernel recovery. |
| 4 | **Server edition has no desktop dependency** | A `server` mkosi profile must exist that produces an image with zero desktop packages (no X11, no Wayland, no Plasma, no PipeWire). |

## 2. Current Infrastructure Assessment

### 2.1 What We Have

| Component | Status | Notes |
|-----------|--------|-------|
| `tools/build-vm-final.sh` | Functional but legacy | Builds a Debian/Ubuntu-based disk image from scratch using `ar`, `tar`, `cpio`, `sfdisk`, `mkfs.ext4`, and `objcopy`. Hardwired to Ubuntu Base 24.04 and Debian kernel 6.1.0-49. This is the v0.3/v0.4 pipeline. |
| `tools/build-mkosi-image.sh` | Partially functional | Builds an Arch-based image via mkosi. Stages Rust binaries into `mkosi/mkosi.extra/`, then invokes `mkosi build --force`. The `mkosi.conf` lists `base`, `linux`, `systemd-sysvcompat`, `zram-generator`, `nftables`, `dbus`, `bash`. |
| `mkosi/mkosi.conf` | Minimal | Single flat profile; no edition separation. No `mkosi.repart/` definitions. Kernel command line is embedded. |
| `mkosi/mkosi.postinst.host` | Functional | Enables `systemd-networkd`, `systemd-resolved`, `systemd-oomd`, `optid`, `optid-boot-assess`; masks `systemd-firstboot`. Removes root password lock. |
| `mkosi/mkosi.extra/` | Staged overlay | Contains pre-built `optid`, `optctl`, `optid-boot-assess` binaries, D-Bus service/introspection XML, systemd units, policy.toml, nftables.conf, network config, hostname, os-release, fstab, cgroup-v2 conf, zram-generator conf. |
| `tools/rush-builder.py` | Legacy | 742-line Python builder for the recipe-based system. Produces rootfs from Debian packages, builds GPT images via `systemd-repart`. Will be retired per ADR 0014 once mkosi parity is proven. |
| `recipes/` | Legacy | Recipe TOML files for kernel, optid, systemd, desktop, server. Will be retired with rush-builder. |
| `distro/editions/` | Declarative only | Four `.toml` edition profiles (desktop, laptop, realtime-audio, server) that describe what each edition should contain, but they are not yet consumed by any build tool. |
| `tools/validate-uefi-boot.sh` | Functional | Boots a disk image through OVMF, checks for UKI boot markers in the serial log. |
| `tools/test-rollback.sh` | Functional | Validates UKI boot, rollback entry retention (≥3), and bad-kernel recovery on a copy of `build/disk.raw`. |
| `distro/boot/uki.toml` | Declarative | UKI layout config (BLS type-2, systemd-ukify, rollback_entries=3, GRUB fallback). Not consumed by build tools yet. |
| `distro/sysupdate/` | Declarative | `uki.conf` and `base.conf` for systemd-sysupdate descriptors. Not consumed by build tools yet. |

### 2.2 Key Gaps

1. **No mkosi profiles for editions** — There is a single `mkosi.conf` with no profile layering. We need at minimum a `server` profile that excludes desktop packages.
2. **No installer flow** — Both `build-vm-final.sh` and `build-mkosi-image.sh` produce pre-populated disk images. Neither implements an *install* step that writes the OS onto a blank target disk from within a live environment.
3. **mkosi image has not been validated** — While `build-mkosi-image.sh` exists, there is no evidence in the repo that the mkosi-built Arch image has been booted and validated through `validate-uefi-boot.sh`.
4. **os-release version mismatch** — `mkosi/mkosi.extra/etc/os-release` and `tools/build-vm-final.sh` had stale version strings (now fixed to 0.5.0-beta.1).
5. **No mkosi.repart definitions** — mkosi can use `systemd-repart` definition files for partition layout; these don't exist yet and would give us reproducible, declarative partition tables.
6. **No double-boot test** — No existing test verifies that a system survives two consecutive boots with boot assessment markers persisting.

## 3. Proposed Implementation Plan

### Phase A: mkosi/Arch Image Parity (Prerequisite for All Criteria)

**Goal:** Produce a bootable Arch-based disk image via mkosi that passes `validate-uefi-boot.sh` and `test-rollback.sh`.

#### A1. Enhance `mkosi/mkosi.conf`

**File:** `mkosi/mkosi.conf`

Add the following configuration sections:

```toml
[Partition]
Type=root
Format=ext4
CopyFiles=/
Minimize=yes

[Partition]
Type=esp
Format=vfat
CopyFiles=/boot:/
```

This replaces the flat `Format=disk` output with a proper partition layout using mkosi's native repart integration. The ESP will contain the UKI and systemd-boot; the root partition will contain the rootfs.

**Alternative (simpler):** Keep `Format=disk` and add a `mkosi.repart/` directory with repart definitions that mkosi picks up automatically:

```
mkosi.repart/
  00-ESP.conf      — vfat ESP partition (C12A7328...)
  10-root.conf     — ext4 root partition (4F68BCE3...)
```

**Recommendation:** Use the `mkosi.repart/` approach. It's more declarative, aligns with systemd-repart, and gives us explicit control over partition UUIDs and sizes.

#### A2. Create `mkosi.repart/` Definitions

**New files:**

- `mkosi/mkosi.repart/00-ESP.conf`:
  ```ini
  [Partition]
  Type=esp
  Format=vfat
  Label=RUSHESP
  SizeMinBytes=64M
  SizeMaxBytes=128M
  CopyFiles=/boot:/
  ```
- `mkosi/mkosi.repart/10-root.conf`:
  ```ini
  [Partition]
  Type=root
  Format=ext4
  Label=RushRoot
  CopyFiles=/
  Minimize=yes
  ```

#### A3. Add UKI Build Integration

The mkosi configuration needs `Bootable=yes` (already present) but we need to ensure the UKI is built correctly with the Rush Linux cmdline. Two approaches:

**Option 1 (Recommended):** Let mkosi handle UKI assembly natively. mkosi with `Bootable=yes` on Arch automatically:
- Installs `systemd-boot` to the ESP
- Calls `ukify` to combine the kernel, initrd, and cmdline into a UKI
- Places the UKI at `/EFI/Linux/` on the ESP

We need to add `systemd-boot` and `uki` to the package list in `mkosi.conf`:

```toml
[Content]
Packages=
    base
    linux
    systemd-sysvcompat
    systemd-boot
    ukify
    zram-generator
    nftables
    dbus
    bash
```

And ensure the kernel command line in `mkosi.conf` matches what we use in `build-vm-final.sh`:

```toml
KernelCommandLine=
    systemd.unified_cgroup_hierarchy=1
    cgroup_no_v1=all
    psi=1
    zswap.enabled=1
    root=/dev/vda2
    rw
    console=ttyS0,115200
    systemd.firstboot=no
```

**Note:** The `root=` parameter may need adjustment for the mkosi image since partition discovery may differ. mkosi can use `root=PARTUUID=...` or we can use `root=auto` with systemd-gpt-auto-generator. For VM testing, `root=/dev/vda2` is acceptable.

#### A4. Update `tools/build-mkosi-image.sh`

Refactor the script to:

1. Dynamically read the version from `VERSION` instead of hardcoding it in `os-release`.
2. Generate `os-release` from a template using the `VERSION` file.
3. Ensure the staging directory (`mkosi.extra/`) is fully populated before invoking `mkosi build`.
4. Add a `--edition` flag that selects the mkosi profile (default: `server`).
5. Add cleanup of `build/` artifacts before rebuild.

#### A5. Validate mkosi Image

Run the mkosi-built image through existing validation:

```bash
sudo bash tools/build-mkosi-image.sh
tools/validate-uefi-boot.sh build/disk.raw
tools/test-rollback.sh build/disk.raw
```

**Acceptance:** Both scripts pass without modification on the mkosi-produced image.

### Phase B: Edition Profiles (Criterion 4: Server Has No Desktop Dependency)

**Goal:** Create mkosi profiles so that `server` builds without any desktop packages.

#### B1. Create mkosi Profile Directory Structure

```
mkosi/
  mkosi.conf                  — Base configuration (shared)
  mkosi.conf.d/
    00-base.conf              — Common settings (packages, cmdline, etc.)
  mkosi.profiles/
    server/
      mkosi.conf              — Server-specific overrides (no desktop packages)
    desktop/
      mkosi.conf              — Desktop-specific overrides (Plasma Wayland, etc.)
```

**Note:** mkosi natively supports profiles via `mkosi.profiles/` directories. Each profile's `mkosi.conf` is overlaid on top of the base configuration.

#### B2. Server Profile

**File:** `mkosi/mkosi.profiles/server/mkosi.conf`

```toml
[Content]
Packages=
    # No desktop packages
    # Base + kernel + headless services only

[Output]
ImageId=rush-linux-server
```

The server profile inherits all base packages from the main `mkosi.conf` but explicitly excludes desktop components. Since we control the package list, we simply don't add any desktop packages.

**Verification:** After building, inspect the image:
```bash
sudo mkosi -p server build
# Then check for desktop packages in the image:
mkosi -p server shell -- pacman -Qg base 2>/dev/null | grep -E '(plasma|wayland|pipewire|xorg)' && echo "FAIL: desktop packages found" || echo "PASS: no desktop packages"
```

#### B3. Document the Profile System

Update `docs/packaging-and-builds.md` to document the mkosi profile architecture and how editions map to profiles.

### Phase C: Installer Flow (Criterion 1: Fresh VM Install Succeeds)

**Goal:** Implement a minimal installer that can write the OS onto a blank disk from a live environment.

This is the most architecturally significant new capability. The approach should respect ADR 0014's "image-based Base OS plane" principle — we're not building an Anaconda-style package-level installer; we're implementing an *image writer* that stamps a pre-built OS image onto a target disk.

#### C1. Design: Two-Image Model

We produce two disk images:

1. **Live/Installer Image** (`rush-linux-live.raw`) — A minimal bootable image that boots to a shell with `rush-install` available.
2. **Target OS Image** (`rush-linux-server.raw`) — The actual OS image that gets written to the target disk.

The install flow:
1. Boot the Live image in QEMU.
2. Run `rush-install /dev/vda` from the live environment.
3. `rush-install` writes the OS image to the target disk using `systemd-repart --copy-from=`.
4. Reboot into the installed system.

**Alternative (Simpler for v0.5):** Instead of a separate live image, we use `systemd-repart` with `--copy-source` to create an installable image from the build output. This means:

1. Build the OS image with mkosi (produces `disk.raw`).
2. Create a *minimal* install wrapper script that uses `systemd-repart` to copy the root partition to a new disk.
3. Validate by creating a blank disk, "installing" to it, and booting.

**Recommended approach for v0.5:** The simpler alternative. We don't need a full live CD for this milestone; we need to prove that an image can be *installed* (i.e., written to a blank disk) and the result boots. This can be validated entirely from the host with `systemd-repart`.

#### C2. Implement `tools/rush-install.sh`

**New file:** `tools/rush-install.sh`

```bash
#!/usr/bin/env bash
# rush-install — Install Rush Linux onto a target block device.
#
# Usage:
#   sudo bash tools/rush-install.sh <source_disk.raw> <target_device>
#
# This script:
#   1. Repartitions the target device using systemd-repart definitions
#   2. Copies the ESP and root partitions from the source image
#   3. Installs systemd-boot
#   4. Verifies the result
#
# The target device is fully overwritten. Use with caution.
```

Key operations:
1. Wipe the target device and create GPT partition table.
2. Use `systemd-repart --empty=create --definitions=mkosi/mkosi.repart/` to create partitions on the target.
3. Copy the ESP contents (UKI, bootloader) from the source image.
4. Copy the root filesystem from the source image using `systemd-repart --copy-source=`.
5. Install systemd-boot to the ESP.
6. Verify partition layout.

#### C3. Implement `tools/test-install.sh`

**New file:** `tools/test-install.sh`

Automated end-to-end install test:

1. Build the OS image: `sudo bash tools/build-mkosi-image.sh`
2. Create a blank 2GB raw disk image.
3. Run `rush-install.sh` to install the OS onto the blank disk.
4. Boot the installed disk with `validate-uefi-boot.sh` and verify it reaches `multi-user.target`.
5. Reboot a second time and verify again (Criterion 2).

### Phase D: Double-Boot and Update/Rollback Tests (Criteria 2 & 3)

#### D1. Implement `tools/test-double-boot.sh`

**New file:** `tools/test-double-boot.sh`

```bash
#!/usr/bin/env bash
# Test that an installed Rush Linux system boots twice cleanly.
#
# 1. Boot the disk image, wait for multi-user.target, poweroff.
# 2. Boot the same disk image again, verify multi-user.target reached.
# 3. Verify boot-assessment marker exists from both boots.
```

This script:
1. Boots the disk image with QEMU/OVMF.
2. Watches for `multi-user.target` and `optid.service` in the serial log.
3. Sends `poweroff` via the QEMU monitor.
4. Boots the *same* disk image again.
5. Verifies `multi-user.target` is reached a second time.
6. Checks that `optid-boot-assess` wrote a boot-good marker.

#### D2. Extend `tools/test-rollback.sh` for mkosi Image

The existing `test-rollback.sh` should work as-is on the mkosi-produced `disk.raw`. The only potential issue is if the ESP partition offset differs between the `build-vm-final.sh` (hardwired 1048576) and mkosi images. We should:

1. Make the ESP offset detection dynamic (use `sgdisk -i 1` to find partition 1 start sector).
2. Validate `test-rollback.sh` passes on the mkosi-built image.

## 7. Risk Assessment

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| mkosi Arch image doesn't boot (missing drivers, fstab issues) | Medium | Test iteratively; Arch kernel has most drivers built-in, so initrd issues should be minimal. The `root=/dev/vda2` fstab may need adjustment to use PARTUUID. |
| `systemd-repart --copy-source` requires root | High | This is expected; the install flow inherently requires root. Document clearly. |
| mkosi version compatibility | Low | Pin mkosi version in documentation. Arch's mkosi package is typically current. |
| Boot assessment marker doesn't persist across QEMU reboots | Low | The marker is written to `/var/lib/optid/boot-assess/` on the rootfs, which persists across VM reboots since QEMU uses the same disk. |
| `test-rollback.sh` ESP offset assumption breaks | Medium | Fix by using `sgdisk` to dynamically find partition 1 start sector. |

## 8. What We Are NOT Doing (Explicitly Out of Scope)

- **No GUI installer** — v0.5.0-beta.1 requires a *fresh VM install* that succeeds, not a user-friendly installer.
- **No `rushbench` / hardware telemetry work** — Per project context, this belongs to v0.6.0-beta.1 and v0.8.0-beta.1.
- **No desktop edition build** — v0.5 requires only the server edition. Desktop is v0.7.
- **No Secure Boot enrollment** — Testing keys only; real enrollment is v0.9.
- **No retirement of `tools/rush-builder.py` and `recipes/`** — That happens after mkosi parity is proven (part of this milestone's validation), but the actual deletion should be a separate, clean commit after the milestone closes.
- **No mkosi sandbox/pacman cache configuration** — These are optimizations for CI; not required for milestone validation.
