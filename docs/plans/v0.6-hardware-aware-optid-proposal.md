## 0. Context

v0.5.0-beta.1 is now genuinely complete. PR #174 committed the four outstanding
build-host acceptance transcripts (`release/evidence/v0.5.0-beta.1/{c1,c2,c3}/`
plus the existing `c4-server-no-desktop`), `tools/dragnet.py --observe` is green,
and `release/milestones.toml` is the honest source of truth.

The next milestone, **v0.6.0-beta.1 — Hardware-Aware optid**, is the first
milestone whose exit criteria cannot be satisfied from a container. It introduces:

1. A hardware allowlist that gates which kernel knobs `optid` may touch.
2. Compatibility D-Bus shims for `power-profiles-daemon` (PPD) and `GameMode`,
   so existing desktop software drives `optid` without code changes on their side.
3. Foreground-application detection so the optimizer can promote the active
   window's class without requiring an explicit `optctl pin`.
4. A VM-guest workload class — PSI is largely meaningless under virtualization
   and the current classifier misjudges guest workloads.
5. The first *quantitative* criteria: "mixed-load responsiveness improves on two
   machines" and "battery behavior matches or improves mainstream defaults."

This proposal mirrors the 5-phase shape of the v0.5 proposal (Phase A through
Phase E), assigns a Builder/Verifier split per `docs/agent-protocol.md`, and
keeps every change behind `--apply` (default remains dry-run).

**Critical correction:** Phase A (hardware allowlist foundation) is largely
DONE on `main` as WP-N4. See §2.1 and §3 Phase A for what's actually left.

## 1. Exit Criteria Recap

Per `release/milestones.toml`, the four exit criteria for v0.6.0-beta.1 are:

| # | Criterion | Implication |
|---|-----------|-------------|
| 1 | **Unsupported knobs are skipped with reasons** | `optid` must consult a hardware allowlist before every write. Anything not in the allowlist for the detected hardware is skipped and the skip is logged with a concrete reason (unknown HWID, deny entry, max_state cap, conflicting daemon, etc.). |
| 2 | **Mixed-load responsiveness improves on two machines** | We need two physical reference machines, a defined mixed-load workload, a baseline (mainstream distro defaults), and `rushbench` transcripts showing `optid --apply` reduces measured latency without regressing throughput. |
| 3 | **Battery behavior matches or improves mainstream defaults** | On at least one battery-equipped reference machine, `rushbench` energy-window transcripts must show `optid --apply` does not increase energy per workload unit vs. the distro default (PPD `balanced`). |
| 4 | **No unsafe write occurs outside allowlisted paths** | A test harness enumerates every sysfs/procfs/devfs path `optid` opens with write intent and asserts each path passes both the ADR-0009 *write* allowlist (`io_util::guarded_write`) AND the WP-N4 *hardware* allowlist (`allowlist::Allowlist::check`) for the host's HWID. |

### 2.2 Key Gaps

1. **Allowlist gate is opt-in, not default-on.** WP-N4 landed with
   `--allowlist=disabled` as the default per research 0006 §7 medium-term plan
   ("Promote from WIP to Validated once seeded baseline covers ≥ 5 laptops ×
   ≥ 3 HWIDs each and all §4 experiments are closed"). v0.6 must flip this to
   enabled-by-default after Phase D validates the seeded baseline on at least
   two reference machines.
2. **No PPD compatibility shim** — GNOME and KDE power sliders speak
   `net.hadess.PowerProfiles`. Without this shim, desktop users who install
   Rush get nothing from their slider.
3. **No GameMode compatibility shim** — Steam games call
   `com.feralinteractive.GameMode.RegisterGame` on launch. Without this shim,
   games don't auto-promote to `latency-critical`.
4. **No foreground detection** — Currently class promotion requires
   `optctl pin <app> <class>`. v0.6 needs automatic promotion of the
   foreground window.
5. **No VM-guest class** — `vm.*` workload class is mentioned in the roadmap
   but has no policy or sensor weighting. PSI under KVM is misleading.
6. **No published baselines** — Without baselines from two machines running
   mainstream defaults, "improves on two machines" is unverifiable. The
   existing 2026-06-10-victus sample is explicitly NOT milestone evidence.
7. **No conflict-detection** — If `tlp`, `tuned`, or `ppd` are running,
   `optid --apply` will fight them. v0.6 must detect and refuse (or mask).
   Note: `config/optid/policy.toml` already declares `competing_policy_daemons`
   but enforcement is not yet wired.
8. **No Criterion 4 enumeration harness.** The allowlist gates exist but there
   is no test that proves Criterion 4 ("no unsafe write outside allowlisted
   paths") by enumerating every write site and asserting each is gated. v0.6
   adds this harness as Phase A's only new code.

## 3. Proposed Implementation Plan

### Phase A: Allowlist Default-Flip + Criterion 4 Harness (Prerequisite for All Criteria)

**Goal:** Verify the WP-N4 allowlist foundation is correct as-implemented, flip
the `--allowlist` default from `disabled` to `enabled`, and add the Criterion 4
enumeration harness that proves no ungated write site exists. After Phase A,
`optid --apply` on any host enforces default-deny with logged reasons, and a
single test mechanically proves Criterion 4.

**Phase A is mostly verify-and-flip, not build.** WP-N4 landed the schema, the
detection, the gate, the tests, and the optctl surface. Phase A's net new code
is one test file.

#### A1. Verify the WP-N4 implementation matches research 0006

**Action:** Builder reads the following in cold checkout and confirms each
claim in §2.1 above is accurate:

- `crates/optid/src/allowlist.rs` — `Allowlist::check` API, default-deny, reason strings
- `crates/optid/data/allowlist.toml` — schema matches Decision 7 of research 0006
- `crates/optid/build.rs` — codegen pattern
- `crates/optid/src/actuator.rs` — `allowlist` field, `enable_allowlist`, every write site consults the gate
- `crates/optid/src/main.rs` — `--allowlist` flag wiring
- `crates/optctl/src/allow.rs` — `allow` / `deny` / `list-allow` subcommands
- `crates/optctl/src/main.rs` — `explain` subcommand + D-Bus proxy

**Output:** `VERIFICATION.md` with the literal output of
`cargo test -p optid allowlist` and `cargo test -p optctl allow`. If any claim
in §2.1 is inaccurate, Phase A expands to fix the discrepancy before A2-A4
proceed. Per the Evidence Rule, the Builder does not self-certify — a separate
Verifier session runs the same commands on a cold checkout.

#### A2. Add the Criterion 4 enumeration harness

**New file:** `crates/optid/tests/write_site_gating.rs`

Integration test (uses `cargo test --test write_site_gating`) that:

1. Compiles a list of every `guarded_write` / `atomic_write_state_file` /
   `Allowlist::check` call site in `crates/optid/src/` via a `grep`-driven
   inventory (or a `#[doc(hidden)] pub const WRITE_SITES: &[&str]` table
   maintained next to the call sites — pick the cheaper option).
2. For each call site, asserts the surrounding code path either:
   - calls `Allowlist::check(...)` and skips on `Verdict::Deny`, OR
   - is on the ADR-0009 always-safe baseline (e.g. `/proc/sys/vm/swappiness`
     when ZRAM is detected — paths that are safe regardless of HWID), OR
   - is a state-file write (not a kernel write — `atomic_write_state_file`).
3. Fails with a literal list of ungated write sites if any exist.

This is the mechanical proof for Criterion 4. It runs in-container; no
hardware needed.

**Acceptance:** `cargo test --test write_site_gating` green; the test
output explicitly enumerates every gated write site.

#### A3. Flip the `--allowlist` default to enabled

**Modify:** `crates/optid/src/main.rs` (the `--allowlist` flag parser) and
`docs/research/0006-hw-allowlist-db-design.md` §7 (move the medium-term
"flip default" item to "Done in v0.6 Phase A").

The flag stays as an escape hatch (`--no-allowlist` for emergency
bypass during bring-up), but the default flips. This is the single
behavioural change in Phase A.

After A3, on a fresh boot:
- `optid` (dry-run) logs intended actions with allowlist verdicts.
- `optid --apply` enforces default-deny on every write.
- `optctl explain` shows the per-action allow/deny verdict in the
  decision trail.

**Acceptance:** `cargo test -p optid` green (existing tests assert
`--allowlist=disabled` behaviour; update them to assert the new default
and add a `--no-allowlist` opt-out test). The behavioural flip is one
commit, separately reviewable.

#### A4. Sanity: no regression on `optctl explain` skip-reason trail

**Action:** Verify the existing `optctl explain` skip-reason trail still
emits a reason per skipped path. The original proposal said "modify
`crates/optctl/src/explain.rs`" — that file doesn't exist; explain is
split across `action.rs`, `policy.rs`, `main.rs`, and `allowlist.rs`.
Phase A's only addition here is a manual smoke-test step in the Verifier's
`VERIFICATION.md`: construct a fixture where one path is allowed and one
is denied, run `optctl explain`, confirm both appear with reasons.

**Acceptance:** Verifier's `VERIFICATION.md` includes the literal
`optctl explain` output for the allowed+denied fixture. No code change
unless the output is missing reasons — in which case Phase A expands to
fix the regression.

#### A5. Test

Tests are already in place from WP-N4 (10 inline `#[test]` functions in
`crates/optid/src/allowlist.rs`). Phase A adds:

- `crates/optid/tests/write_site_gating.rs` (new, from A2) — Criterion 4
  enumeration harness.
- One new inline test in `allowlist.rs` asserting the default-on behaviour
  when `--allowlist` is not passed (covers A3).

**Acceptance:** `cargo test -p optid` green; `cargo test --test write_site_gating`
green; `cargo test -p optctl` green.

**Phase A satisfies Criterion 1 (full — every write is gated and skip
reasons are emitted) and Criterion 4 (full — the enumeration harness
proves no ungated write site exists).**

### Phase B: PPD and GameMode Compatibility Shims (Criterion 1 partial, enabler for desktop editions in v0.7)

**Goal:** Implement `net.hadess.PowerProfiles` and `com.feralinteractive.GameMode`
D-Bus interfaces on the `optid` D-Bus name, so existing desktop software drives
`optid` mode changes without forking PPD or GameMode.

#### B1. PPD shim (`net.hadess.PowerProfiles`)

**New module:** `crates/optid/src/shim/ppd.rs`

Implements:
- `org.freedesktop.DBus.Properties.Get("net.hadess.PowerProfiles", "ActiveProfile")`
- `Set` for the same.
- `org.freedesktop.DBus.Properties.Get("net.hadess.PowerProfiles", "Profiles")`
  returning `[{Profile:"power-saver"}, {Profile:"balanced"}, {Profile:"performance"}]`.
- `HoldProfile` / `ReleaseProfile` — PPD's API for transient claims.

Mapping (configurable via `policy.toml`):

| PPD profile | optid mode |
|-------------|------------|
| `power-saver` | `--pin class=idle` |
| `balanced` | (clear all pins; revert to classifier) |
| `performance` | `--pin class=throughput` |

GNOME Settings → Power slider now drives `optid` directly. KDE's `powerdevil`
speaks the same interface.

#### B2. GameMode shim (`com.feralinteractive.GameMode`)

**New module:** `crates/optid/src/shim/gamemode.rs`

Implements:
- `RegisterGame(pid)`
- `UnregisterGame(pid)`
- `QueryStatus()`
- `QueryStatusClient(pid)`

On `RegisterGame(pid)`, `optid` issues an implicit `pin <pid> latency-critical`
with a TTL of 30 minutes (configurable). On `UnregisterGame(pid)`, the pin is
released. Steam, Lutris, and Heroic already speak this interface; no client
changes are needed.

#### B3. Conflict detection

**New module:** `crates/optid/src/shim/conflict.rs`

On startup, `optid` checks for running daemons that conflict with the shims:
- `tlp.service` → log error, refuse `--apply` until masked.
- `tuned.service` → same.
- `power-profiles-daemon.service` → log error: "PPD is running. Either stop
  PPD (recommended, optid provides the PPD interface) or stop optid's PPD shim
  via `--no-shim=ppd`."

This protects Criterion 4: if two daemons fight over `/sys/firmware/acpi/platform_profile`,
both can produce inconsistent writes — exactly what the allowlist is meant to
prevent. The conflict check is itself part of the allowlist enforcement.

Note: `config/optid/policy.toml` already declares `competing_policy_daemons =
["tlp.service", "power-profiles-daemon.service", "tuned.service"]` — Phase B
wires the actual enforcement of that list.

#### B4. Test

**New file:** `crates/optid/tests/shim_ppd.rs`, `crates/optid/tests/shim_gamemode.rs`

Use `zbus` test bindings to validate the D-Bus interfaces respond correctly
without a real session bus. All in-container.

**Acceptance:** `cargo test -p optid shim_` green. Manual: `gdbus call --session
--dest io.rushlinux.Optid1 --object-path /net/hadess/PowerProfiles
--method org.freedesktop.DBus.Properties.Get net.hadess.PowerProfiles ActiveProfile`
returns the current mode.

### Phase C: Foreground Detection and VM-Guest Class (Criterion 1 cont., enables Criterion 2)

**Goal:** Replace the explicit `optctl pin` model with automatic foreground
promotion for desktop sessions, and add a `vm.guest` workload class so the
classifier doesn't misjudge KVM guests.

#### C1. Foreground detection via `logind` + `wayland`

**New module:** `crates/optid/src/foreground/mod.rs`

Strategy:
1. Subscribe to `org.freedesktop.login1` `SessionNew` / `SessionRemoved`.
2. For each new session, check `Active` and `Class` (= "user").
3. If the session is `Type=wayland` or `Type=x11`, subscribe to the compositor's
   focus signal:
   - Wayland: `org.gnome.Mutter.IdleMonitor` (GNOME) / `org.kde.KWin` (KDE) —
     or fall back to `wlr-foreign-toplevel-management` (wlroots/sway/Hyprland).
   - X11: `_NET_ACTIVE_WINDOW` root window property via `xcb`.
4. On focus change, issue `pin <pid-of-focused-window> <class>` where `class`
   comes from `policy.toml` `[foreground.*]` rules (e.g., browser=interactive,
   IDE=throughput, game=latency-critical).

For v0.6 the foreground rules are minimal — just "game window → latency-critical,
everything else → no override." Elaboration deferred to v0.7.

#### C2. `vm.guest` workload class

**Modify:** `crates/optid/src/classifier/mod.rs` (or wherever the classifier
module lives at the time Phase C lands — verify path before implementation)

Add a sixth class `vm.guest`. The classifier detects VMs via DMI (`sys_vendor ==
QEMU|KVM|VMware|Xen|Microsoft`) and, when in a VM, uses a different sensor
weighting:
- PSI avg10 is multiplied by 0.5 (the hypervisor's scheduler distorts it).
- `loadavg` is the primary signal.
- `latency-critical` is downgraded to `interactive` (we can't enforce real
  latency floors in a guest anyway — PM QoS to the host CPU doesn't propagate).

The `vm.guest` class is *not* user-selectable via `optctl pin` — it's forced by
the platform detector. This prevents a user from pinning a guest to
`latency-critical` and expecting host-level behavior.

#### C3. Test

Foreground detection is hard to unit-test (requires a compositor). For v0.6,
scope the test to: the `foreground` module compiles, exposes a `subscribe()`
function that returns a stream of `(pid, class)` events, and the `policy.toml`
parser accepts `[foreground.*]` rules. Real-compositor testing is deferred to
v0.7 when we have a desktop edition.

VM-guest class is fully unit-testable: feed a fixture where DMI says QEMU and
verify the classifier selects `vm.guest`.

**Acceptance:** `cargo test -p optid vm_guest` green. Foreground detection
compiles and is wired into `optid` behind a `--foreground=auto|off` flag
(default `off` for v0.6; `auto` becomes default in v0.7).

### Phase D: Reference Machines, Baselines, and Benchmark Transcripts (Criteria 2 & 3)

**Goal:** Produce the first published `rushbench` transcripts: baselines from
two physical machines running mainstream defaults, then `optid --apply` runs
on the same two machines, and a comparison.

This is the heaviest phase and the one with the most external dependencies.
It cannot be done by an agent alone.

#### D1. Nominate two reference machines

**Decision required from project owner before this phase starts:**

| Slot | Suggested profile | Why |
|------|-------------------|-----|
| Desktop | Modern Intel or AMD, 6+ cores, discrete GPU, on AC always | Tests throughput class, latency-critical (gaming), no battery criterion |
| Laptop | Modern Intel laptop (U-class), iGPU, battery, AC + battery modes | Tests battery criterion (Criterion 3), idle/light classes, platform_profile on real hardware |

One laptop candidate is already in the loop: the HP Victus (i7-13700HX, 24
cores, Fedora 44) that produced the defective 2026-06-10 sample. The project
owner can either re-use it (with proper capture this time) or nominate a
different laptop. Either way, the existing sample is **not** evidence — its
defects are documented in `release/evidence/host-bench/2026-06-10-victus/NOTE.md`.

The project owner must confirm: (a) which specific machines, (b) who has
physical access, (c) which distro is the baseline (suggested: Ubuntu 24.04
LTS with default PPD `balanced` profile — the most common mainstream default).

Document the choice in `docs/strategy/reference-hardware.md` (new file).

#### D2. Define the mixed-load workload

**New file:** `docs/strategy/mixed-load-workload.md`

The workload must exercise all four active classes in a single run so the
optimizer's class transitions are observable. Suggested mix:

1. **Idle** (60s): nothing.
2. **Interactive** (60s): `firefox` rendering a JavaScript benchmark.
3. **Throughput** (60s): `ninja -C build` on a medium C++ project.
4. **Latency-critical** (60s): `glmark2` fullscreen at 60 FPS target.
5. **Idle** (30s): cool-down.

Repeat ×5 for stability. Total: ~30 minutes per run.

`rushbench` already supports structured energy windows and N-sample collection;
this phase wires the workload definition into `rushbench` as a named preset
(`rushbench run preset=mixed-load-001`).

#### D3. Baseline runs

For each reference machine:
1. Install the baseline distro (Ubuntu 24.04 LTS, default install, default PPD).
2. Run `rushbench run preset=mixed-load-001 --tag=baseline-ubuntu-2404-<hostname>`.
3. Commit `meta.txt` + `transcript.log` + `results.csv` to
   `release/evidence/host-bench/<date>-<hostname>/baseline/`.

These baselines are not optid-specific; they are the comparison point for the
v0.6 release. They will also serve v0.8 (Benchmark Lab).

#### D4. optid runs

For each reference machine:
1. Install Rush Linux v0.6.0-beta.1 (server edition is fine for the desktop
   machine; we don't need a desktop for these tests — the workload is launched
   from a TTY).
2. Boot with `optid` in dry-run mode. Confirm `optctl status` is green.
3. Enable `optid --apply` via `optctl mode apply`. Allowlist is enabled by
   default (Phase A3); seeded baseline covers the test machines' HWIDs.
4. Re-run `rushbench run preset=mixed-load-001 --tag=optid-0.6.0-beta.1-<hostname>`.
5. Commit transcripts to `release/evidence/host-bench/<date>-<hostname>/optid/`.

#### D5. Comparison and verdict

For each machine:
1. Compute the delta between baseline and optid runs:
   - Latency: PSI avg10 mean and p99 per phase.
   - Energy: joules per phase, joules per workload unit.
2. Write `release/evidence/host-bench/<date>-<hostname>/VERDICT.md`:
   - "Criterion 2 (mixed-load responsiveness improves): PASS / FAIL — <evidence>"
   - "Criterion 3 (battery behavior matches or improves): PASS / FAIL / N/A — <evidence>"
3. Update `release/milestones.toml` criteria_status rows for v0.6.

**Acceptance:** Both machines have committed transcripts in
`release/evidence/host-bench/`. `tools/dragnet.py --observe` is green. The
verdict text in each `VERDICT.md` is the literal source for the
`milestones.toml` `note` field.

**Phase D satisfies Criteria 2 & 3.** Phase D also validates the seeded
allowlist baseline (research 0006 §4 evidence gaps close here), which unblocks
the research 0006 §7 promotion from WIP to Validated.

## 7. Risk Assessment

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Reference machines not nominated → Phase D stalls | High | Phase D1 is a hard gate; surface it to the project owner in the PR description for Phase A so they have weeks of lead time |
| Flipping `--allowlist` default to on breaks existing CI fixtures that assumed dry-run-by-default | Medium | A3 is a single commit, separately reviewable; update fixtures in the same commit; Verifier runs the full `cargo test --workspace` |
| `systemd-logind` D-Bus subscription is unstable across compositors | Medium | Ship foreground detection as `--foreground=off` default in v0.6; flip to `auto` in v0.7 after broader testing |
| PPD API drift between GNOME/KDE versions | Low | Pin to the documented `net.hadess.PowerProfiles` API (stable since 2021); add a shim test that exercises the interface against a mock |
| `vm.guest` class masks real performance issues in CI | Medium | The classifier logs which class is active; CI runs that show `vm.guest` should be flagged for human review |
| `rushbench` baselines vary more than the optid delta | High | Use 5-sample runs (already supported); compute confidence intervals; report PASS only if the delta exceeds the confidence interval |
| Battery criterion is N/A on the desktop machine | Medium | `VERDICT.md` explicitly permits N/A on non-battery hosts; Criterion 3 then rests on the laptop alone |
| Seeded allowlist baseline too thin for default-on | Medium | Research 0006 §7 medium-term plan said "≥ 5 laptops × ≥ 3 HWIDs each" before flip; v0.6 relaxes this to "2 reference machines validated in Phase D" — document the relaxation in research 0006 §7 |

## 8. What We Are NOT Doing (Explicitly Out of Scope for v0.6)

- **No desktop edition build** — That is v0.7. The PPD/GameMode shims land in
  v0.6 but they are tested against a headless server edition; full desktop
  testing happens in v0.7.
- **No laptop-specific power policy** — Laptop edition lands in v0.7. The
  battery criterion in v0.6 is satisfied by running the server edition on the
  laptop; the optimizer's behavior is the same.
- **No realtime audio edition** — v0.7.
- **No published benchmark report** — v0.8 (Benchmark Lab). v0.6 only produces
  the transcripts; v0.8 turns them into a published artifact.
- **No automatic conflict masking** — `optid` reports conflicts; the user
  decides whether to mask. Auto-masking is policy territory.
- **No Secure Boot enrollment** — Testing keys only; real enrollment is v0.9.
- **No `optctl pin --ttl`** — Pins are still explicit-release. TTL-based
  release is a v0.7 consideration once GameMode integration has shipped.
- **No new sched_ext scheduler** — We continue to use EEVDF as the verified
  fallback. A Rush-specific `sched_ext` program is a v0.8+ research item.
- **No reimplementation of the WP-N4 allowlist.** The schema, detection, gate,
  tests, and optctl surface landed in WP-N4. v0.6 Phase A only verifies,
  flips the default, and adds the Criterion 4 harness. Any rewrite of the
  allowlist itself is explicitly out of scope.

## 10. Open Questions for the Project Owner

1. **Which two reference machines?** Suggested: one Intel desktop (i5-13400 or
   similar), one Intel laptop (ThinkPad X1 or similar). One laptop candidate
   (HP Victus, i7-13700HX) is already in the loop but produced a defective
   sample. Confirm before Phase A merges so D1 isn't a blocker.
2. **Which baseline distro?** Suggested: Ubuntu 24.04 LTS with default PPD
   `balanced`. Alternative: Fedora 44 with default PPD (the Victus already
   runs Fedora 44). Pick one and stick with it for v0.6 and v0.8.
3. **Is `--foreground=off` acceptable as the v0.6 default?** The alternative
   is `auto`, which is more impressive but riskier.
4. **Conflict masking: should `optid` refuse to start, or start in dry-run?**
   Current proposal: dry-run. Alternative: hard refusal.
5. **PPD and GameMode shims: should they be on by default, or behind
   `--shim=ppd,gamemode`?** Current proposal: on by default, behind
   `--no-shim=...` for opt-out.
6. **Relaxing research 0006 §7's "≥ 5 laptops × ≥ 3 HWIDs" gate for the
   default-flip.** v0.6 Phase D validates on 2 reference machines. Is that
   sufficient to flip the default, or should the default stay `disabled`
   through v0.6 and flip in v0.7?

Answers can be inline comments on the PR that lands this proposal.
